# Bundled detector references

The application compiles stable visual references into a versioned directory containing `manifest.json` plus compact PNG payloads. The manifest declares the required 808 by 611 Roblox client size, state regions, click actions, selection references, difficulty and node hue prototypes, the empty-hotbar reference, and a SHA-256/size entry for every payload file.

Detector data is application content, not a separately installed product feature. Every portable ZIP and installer contains the exact version selected by `AnimeExpeditionsDetectorSpec.BundledPackVersion`. The app does not check for, download, select, or roll back detector data independently of an application release.

At startup, the bundled manifest and every declared payload are validated before automation can run. A validated copy is synchronized to the application-managed local cache used by runtime and diagnostic tooling. Any older, newer, mismatched, or damaged cached copy is replaced by the data bundled with that application version. A damaged application bundle stops startup with clean-reinstall guidance rather than attempting to run with partial detector coverage.

Release packaging independently validates the published detector manifest, sizes, and hashes before creating the portable archive or installer. `Verify-Release.ps1` repeats those checks against the actual portable ZIP and fails when a reference is absent, misplaced, the wrong size, or hash-mismatched.

## Build from the dataset tool

Run `ExpeditionsMacro.DatasetBuilder`, choose the local dataset root, choose an output folder and semantic version, then select **Build detector pack**.

The command-line equivalent is:

```powershell
dotnet run --project tools/ExpeditionsMacro.DatasetBuilder -- --build datasets/anime-expeditions/expeditions detector-packs 1.0.2
```

## Inspect production detectors

Run `ExpeditionsMacro.DetectorViewer` to inspect a PNG/JPEG/BMP/TIFF, a recursive image folder, or the captured frames in a Deep Debug ZIP. The standalone viewer groups every production detector or recognizer in a searchable catalog and overlays its exact static regions, returned live action, emitted evidence, confidence, and explicit gates.

Inspection is deliberately provenance-safe:

- pass/fail is shown only for a production result, a production-emitted Boolean, or a metric wired to its exact production gate;
- reflected named constants remain advisory when production does not expose their metric association;
- dynamically translated or locally searched geometry is not invented from nearby constants;
- unavailable helper details remain visible with an explicit reason;
- the viewer never changes detector decisions or authorizes input.

See [the Detector Viewer README](../tools/ExpeditionsMacro.DetectorViewer/README.md) for controls and headless validation commands.

After reviewing the generated manifest and payload, update the bundled content entry in `ExpeditionsMacro.App.csproj` and `AnimeExpeditionsDetectorSpec.BundledPackVersion` together. Do not publish the generated directory as an independent release asset.

## Runtime evidence and action ownership

A manifest action coordinate is a fallback location, not proof that its owning UI exists. Every click, drag, or key-triggered navigation boundary must first prove the expected owner from the current canonical frame and, when available, derive the live action from that same detector. An unknown frame, a stale coordinate, or a static manifest point never authorizes input. `ObservationWaitBudgetTests.StaleManifestCoordinatesOnUnknownFramesDoNotAuthorizeAClick`, `ObservationWaitBudgetTests.ExpeditionActionsRequireTheirOwningScreen`, and the full cross-state corpus protect this boundary.

Owned UI waits count completed observations instead of assuming every capture/detector pass finishes inside a short wall-clock soft timeout. A fresh caller-supplied initial frame may count, but a later unowned frame resets pending stability. The separate hard deadline, stable-frame requirement, and existing input-attempt cap remain unchanged. After input, the workflow discards pre-input stability and reacquires fresh owner/action proof; a pending confirmation blocks duplicate and alternate input, and only a verified transition resets an unchanged-owner budget. Challenge, Stage, and Expedition retain three input attempts per unchanged verified owner/action, while Expedition recovery also retains its eighteen-attempt overall cap. These rules are protected by `ObservationWaitBudgetTests.RequiredObservationsSurviveTheSoftDeadline`, `ObservationWaitBudgetTests.LongSoftTimeoutIsNotShortenedByTheHardDeadline`, `ChallengeNavigationInputGateTests.StaticScreen_StopsAfterThreeVerifiedInputAttempts`, `ChallengeNavigationInputGateTests.PendingSlowConfirmation_DoesNotAuthorizeDuplicateInput`, `StageNavigationTransactionStateTests.StaticVerifiedActionStopsAfterThreeAttempts`, `StageNavigationTransactionStateTests.PendingSlowConfirmationBlocksAlternateNavigationInput`, `ChallengeActionRetryTests.SlowActionProof_CannotExceedMaximumParkingAttempts`, and `ExpeditionRecoveryTransitionLoopTests.CyclingStatesStillStopsAtTheOverallAttemptCap`.

Camera preparation does not consume a learned detector pack, yaw atlas, camera model, arrow-pulse reference, or horizontal-yaw matcher. Fast is the only runtime path: standardize the client, clamp maximum zoom, temporarily use the configured Shift Lock binding, and clamp pitch through vertical relative movement without changing yaw. Public camera-model fields remain parse-only compatibility data and are rejected before Roblox discovery or input. `CameraPreparationExecutionPolicyTests.FastNoAlign_IsTheOnlyExecutablePreparationMode`, `CameraPreparationExecutionPolicyTests.CameraModel_StopsExecutionWithActionableGuidance`, `FastOnlyRunnerCompatibilityTests.LegacyExpeditionPreset_StopsBeforeRobloxDiscovery`, `FastOnlyRunnerCompatibilityTests.LegacyChallengePreset_StopsBeforeRobloxDiscovery`, `FastOnlyRunnerCompatibilityTests.LegacyStagePreset_StopsBeforeRobloxDiscovery`, and `CameraPosePreparationServiceTests.PrepareWithoutYaw_ClampsPoseWithoutYawInput` protect that boundary.

## Specialized field revisions

The current app may layer strict specialized detectors over the compiled references for field-confirmed UI revisions. Every specialized detector still consumes canonical 808 by 611 client frames and must carry reviewed fixtures plus cross-state negative coverage.

Fail-closed ownership must come from multiple independent semantic or structural signals, not exact raster placement of a one-pixel decoration or mutable artwork/body brightness. When field evidence establishes a thin line, border, or glyph edge as useful evidence, score the strongest supported sample only inside a narrow reviewed neighborhood and keep the remaining owner-state gates mandatory. OCR is permitted only after structural owner proof has bounded the crop; require confidence plus temporal and semantic validation, and never let OCR alone supply owner or action geometry. Regression coverage must include deterministic one-pixel removal/shift/thickness variants where meaningful, mutable-content brightness changes, and the complete cross-state corpus; broad threshold reductions and unrestricted searches may not authorize input. Fractionally scaled subregions map both half-open edges so a trailing region cannot grow outside its matched owner.

The Roblox Settings gear is detected from its opaque white gear structure at the two fixed Roblox-owned top-bar offsets: center `(232, 34)` without the optional voice slot and `(276, 34)` with it. The detector does not inspect whether that optional slot contains a microphone or headset and does not scale either coordinate with Anime Expeditions UI Scale. It accepts both normal and field-observed high-contrast white gear strokes while retaining spoke/center structure and negative coverage for the adjacent ellipsis and door glyphs. The selected filled gear is independently required when closing Settings. `RobloxSettingsButtonDetectorTests.HighContrastVoiceGear_RemainsClosed`, `RobloxSettingsButtonDetectorTests.HighContrastNoVoiceGear_RemainsClosed`, `RobloxSettingsButtonDetectorTests.HighContrastSelectedGear_RemainsSelected`, `RobloxSettingsButtonDetectorTests.HighContrastEllipsisAndDoorWithoutGear_AreRejected`, `MacroStartupPreflightServiceTests.HighContrastVoiceLayout_StillOpensAndClosesSettings`, and `MacroStartupPreflightServiceTests.HighContrastNoVoiceLayout_StillOpensAndClosesSettings` cover both offsets and the action lifecycle.

Settings-panel ownership requires the scale-aware complete Settings page rail—one cyan selected page plus the repeated neutral unselected page controls—in addition to the red Close component. Variable page-body brightness is supporting confidence, not ownership evidence. The complete rail rejects the structurally similar Areas Lobby and red Event-theme Lobby without making a changing page body a hard gate.

The Roblox chat button is independently detected at fixed center `(139, 34)`. Its speech-bubble top, sides, and tail own the glyph even when a notification badge overlaps the slot; the stable body fill then distinguishes the outlined closed state from the opaque open state. A notification badge alone does not mean chat is open, and a microphone in that slot remains unknown rather than closed. The detector ignores the optional voice-control slot and does not scale the coordinate with Anime Expeditions UI Scale. Automation requires two matching frames before either returning closed or clicking an open button, then requires two fresh closed frames after that input; an ignored click may be retried once. The two committed canonical fixtures retain only the exact privacy-redacted button region. `RobloxChatButtonDetectorTests` and `RobloxChatPanelNormalizerTests` cover all reviewed field frames, adjacent-control negatives, slow observations, ignored input, cancellation, and unknown-state no-input failure.

Areas ownership requires the complete five-action category rail, exactly one selected category, no additional lower rail action, and fresh target-card frame evidence before target input. Decorative panel headers, bottom borders, and mutable page contents do not authorize action. An ordinary resource-station panel requires the station identity accent, red Close component, live **Add Fuel** control, both Building Stats bars, and the Rewards frame structure. The Add Fuel dialog is independently owned by live Max, Confirm, and Cancel controls plus both Stats bars and the Rewards frame. Fuel and Claim contents remain independent. Returned input coordinates follow the observed control or translated owned layout. `ResourceRefuelDetectorTests` protects every reviewed fuel/reward combination and rejects the complete non-Refuel corpus.

Challenge Victory is owned by the independently detected red Close and wide purple **View Party** actions. Animated reward artwork, roster size, reward values, and reward colors are variable and are not ownership gates. A post-match party is owned by its live **Change Gamemode** action; the compact Expedition layout additionally requires the neighboring live **Change Map** action. Variable map and roster brightness is not ownership evidence. `ChallengeScreenDetectorTests.VariableBrightPartyContents_DoNotSuppressLivePostMatchActions`, `ChallengeScreenDetectorTests.VictoryOwnership_DoesNotDependOnRosterRewardColors`, and `ChallengeScreenDetectorTests.UnrelatedCorpus_DoesNotAcquireVictoryOrPostMatchOwnership` protect these boundaries.

The 2026-07-25 Expedition selector uses the cyan perimeter of the active left-side map card, the lower-left difficulty color, and the independently detected live **Select Stage** button while retaining the compiled compact selector as a legacy layout. Its specialized action still requires the current selector owner; a compiled coordinate alone cannot authorize **Select Stage**.

Legacy Expedition map and difficulty fallbacks require the same live wide **Select Stage** component before interpreting active-row markers, hue prototypes, or selection references. Inactive map-card artwork is not averaged or gated; only the live wide Select Stage component and isolated cyan active-row marker own the legacy selection. The current full-screen selector retains its independent left-rail and lower-left live-action proof. Non-selector gameplay, terminal, Play, Challenge, Event, Settings, Refuel, and Stage frames must return no map or difficulty. `PackDetectorOwnershipTests.MapSelectorOwner_RejectsGameplayGreenComponents`, `PackDetectorOwnershipTests.LegacyMapSelection_DoesNotAverageInactiveCardArtwork`, and `PackDetectorOwnershipTests.MapAndDifficultySelections_RequireTheSelectorOwnerAcrossRepresentativeStates` protect those boundaries.

AFK Chamber ownership comes from the aligned bottom action rail: a live yellow **Select Stage** component followed by a live neutral **Return to Lobby** component with matching baseline, gap, and size. The gold **AFK Chamber** title contributes confidence but is not an ownership gate because decorative header rendering can settle independently. The detected neutral component supplies the Return to Lobby action. `PackDetectorOwnershipTests.AfkActionRail_DoesNotRequireTheDecorativeTitle` and `PackDetectorOwnershipTests.AfkActionRail_DoesNotOwnOtherRepresentativeStates` protect that boundary.

Villain Invasion Event pages are specialized because that route is Lobby-only and does not belong to the shared Play-interface state graph. When another Event is selected, its catalog detector requires the wide cyan selected tab and chevron plus the thin red Villain Invasion rail without a chevron; it never scores the changing card artwork. Villain Invasion home requires the wide red selected tab and chevron plus the independent live Event Gamemode button, including its isolated rectangular borders and neutral label. The top and lower button borders use the strongest horizontal row only inside their narrow fixed bands so a one-pixel raster phase or thickness change does not erase otherwise complete button ownership. A red carousel rail crossing the same fixed action region is not button ownership. The decorative red Events header is not required because it can render after those live controls on slower devices. Event Act selector and Act detail may use the retained wide selected Villain Invasion tab at either observed row position as Event context; a thin unselected rail is insufficient. Selector ownership still requires its full-width rail and opaque subtitle, while detail ownership still requires the live Stage detail and Select Stage structure. The shifted Act selector is evaluated before retained Event-home evidence, so a selected tab remaining behind the selector cannot send another Event Gamemode click. `EventScreenDetectorTests.ShiftedActSelector_PrecedesRetainedEventHomeEvidence`, `EventScreenDetectorTests.EventHome_RejectsActCarouselWithoutSelectorHeading`, `EventScreenDetectorTests.EventHome_RequiresSelectedVillainChevron`, `EventScreenDetectorTests.EventHome_DoesNotWaitForDecorativeHeader`, `EventScreenDetectorTests.EventHome_AcceptsOneRenderedTopBorderRow`, and `EventScreenDetectorTests.EventHome_AcceptsOneRenderedBottomBorderRow` protect those boundaries.

Bounty Board ownership requires two independent bounded regions: the aligned neutral **Back** plus blue **Calendar** action rail and the **Bounty Board** header. The ordinary header path uses the wide multi-row gold title structure, while a fixed-crop glyph recognizer tolerates a small local raster shift or changed title hue. The text fallback cannot authorize the Board without the live two-button rail. Changing card artwork, the bronze board body, the top rail, the Event sidebar row, and the daily counter are not Board ownership evidence. The card-action recognizer separately owns usable cards: yellow Reroll and green Claim are actionable, while a card with neither action is dimmed. Card-number matching compares the complete `17×7` suffix support with at most one raster-pixel difference and a three-pixel runner-up margin, preventing a damaged `#10` from becoming `#1`. The insufficient-Gold recognizer requires both the neutral message template and its red alert backing. Wave matching first requires exactly one locally owned counter: the bounded dark pill rails, blue Wave badge, and neutral Wave label must agree at either the retained `(389,48)` or no-voice `(421,28)` layout. Only that owned anchor is searched within ±1 pixel for a number with 70% template coverage and `0.72` Dice. Automation additionally requires the independently detected gameplay hotbar, Unit Manager, and Stage Info controls before a wave can advance safe-exit evidence.

Placement confirmation is another strict specialized detector. A placed unit is accepted only when the fixed lower-left panel exposes both its red Close control and its initial blue **Priority / First** control. The dark panel body contributes confidence but is not sufficient or required on its own, and an ordinary hover/info card must remain a negative.

Saved-team navigation gives Unit Inventory precedence when its independent red Close, red **Unequip All**, purple **Teams**, and yellow **Quick Sell** actions are live. Neither the decorative gold title nor roster/body brightness owns the screen. Green unit artwork can overlap nominal Unit Teams Load-button rows, so changing card content may not override complete Unit Inventory ownership. The live purple Teams component supplies the click coordinate. After input, Unit Teams requires the red Close control, at least two full **Load Team** rows, and a height-bounded scrollbar anchored to that panel. Confirmation ownership requires at least two retained Load rows plus the live modal action or actions; whole-panel darkness remains optional confidence. A one-row raster gap may not split an otherwise field-shaped scrollbar thumb, and an unchanged Unit Inventory authorizes only one bounded retry.

Story and Raid option acknowledgement first requires the existing detail-panel state and live **Select Stage** action, then locates the nearly continuous saturated left option rail. The visually one-pixel rail is accumulated per scanline across only its strongest three-column band, so adjacent raster coverage does not erase ownership while the vertical-support threshold remains unchanged. Story requires one distinct cyan selected row with separation from every other Act/Infinite/Mastery row; only an Act owns difficulty and additionally requires the fixed green **Normal Mode** or red **Hard Mode** label. Infinite and Mastery never authorize a difficulty action, and legacy non-Act Hard values normalize to false. Raid requires one distinct red selected act row. These proofs are evaluated across consecutive frames after the single configured option click.
