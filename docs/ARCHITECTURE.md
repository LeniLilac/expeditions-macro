# Architecture

The application separates reusable automation behavior from the WPF shell:

```text
Core <- Vision ----\
  ^                 \
  +---- Windows -----> Automation -> App
  +-------------------------------> App
```

Project references are allowlisted and checked by `scripts/Test-RepositoryPolicy.ps1`. Adding a project or dependency requires an explicit architecture-policy update; lower layers must never acquire a reference to a higher layer.

- `ExpeditionsMacro.Core` contains immutable geometry, image, model, preset, persistence, and workflow contracts.
- `ExpeditionsMacro.Windows` owns Win32 window discovery, per-monitor effective-DPI validation, exact client sizing, Windows Graphics Capture of the Roblox compositor surface, FP16 scRGB-to-SDR conversion, bounded GDI capture for the explicit desktop region selector, DPAPI, configurable key input, Roblox-compatible mouse nudging and acknowledged client-control drags, Roblox `O`-key zoom with a wheel fallback, extended scan-code camera arrows, and relative right-drag fine camera input. The global hotkey accepts safe single-key letters, digits, punctuation, numpad keys, and supported function keys. Shift Lock resolves the saved virtual key to a physical scan code and preserves extended-key identity, so Left/Right Shift and Left/Right Ctrl remain distinct.
- `ExpeditionsMacro.Vision` owns lighting-normalized scoring, temporal medians, detector-pack compilation, validation, classification, Expedition, Challenge, and supported Event states, Story/Raid stage navigation, saved-team dialogs, map and difficulty selection, node hues, and hotbar checks.
- `ExpeditionsMacro.Automation` owns camera calibration/alignment, placement recording/playback, saved-team loading, the Expedition, Challenge, Story, Raid, and supported Event runners, the prioritized Macro scheduler, recovery, Discord Components V2, and detector updates.
- `ExpeditionsMacro.App` is the single WPF interface and exclusive input-owner coordinator.
- `ExpeditionsMacro.DatasetBuilder` compiles a local capture corpus into a small, hashed detector pack.

All saved coordinates are relative to the Roblox client. Camera calibration and placement recording use the canonical 808 by 611 detector size. Camera setup standardizes zoom and pitch, snapshots the globally configured Shift Lock key for balanced enable/cleanup, and selects stable map regions while preserving left/center/right evidence. Schema 4 calibration captures the signed fine-yaw neighborhood with atomic gestures, treats its verified stationary return as the authoritative zero, then holds Right Arrow once and samples a dense full turn at up to roughly 60 frames per second. A compact regional luminance/texture/gradient descriptor locates the returning neighborhood; acceptance additionally requires either a matching signed fine-yaw reference or an exact registered structural match. If sampling skips that first seam and recognizes a later seam instead, setup compares distributed fingerprint and registered-landmark pairs across the two candidate revolutions and retains only the first period when the repetition is independently proven. Because the game can continue rotating between the recognized callback frame and key release, setup then locates the stationary pose in the completed atlas and returns through bounded, re-observed arrow groups before fine verification. A bounded discrete-pulse probe searches only physically possible forward atlas ranges and measures the conversion between dense visual bins and arrow pulses, rather than assuming continuous hold time and repeated taps have identical rates. Its return uses the same atlas feedback instead of assuming equal opposing pulse counts are visually reversible. When a fine-mouse correction independently restores the full-resolution goal beside the circular atlas seam, that visual verification completes the return even if the coarse atlas still labels the pose as one bin left or right of zero. Normal setup has a tested sub-20-second performance goal, while a separate 120-second internal cancellation boundary handles a permanently stalled capture or game; model saving remains transactional. Schema 3 pulse atlases remain loadable.

Runtime alignment converts a dense atlas match back to pulse distance and uses the saved full-turn atlas for coarse correction plus the saved fine atlas before its live micro-search. Coarse correction is closed-loop: it sends at most six arrow pulses, re-observes the actual atlas position, and recalculates the shortest remaining direction after each group. Setup restoration is more conservative: it sends at most three pulses, halves the estimated remainder near zero, and constrains the next lookup to the physically reachable circular neighborhood before falling back to a global match. Fingerprint isolation excludes a density-scaled angular neighborhood rather than a fixed frame count, so capturing more atlas samples cannot turn adjacent yaws into false remote duplicates. A dense fingerprint may earn this bounded feedback path when it is both strong and isolated from every remote yaw neighborhood, even if the continuously moving setup frame has lower registered structure; a known prior position plus bounded input may supply that locality during setup restoration. Weak structure, a non-unique unconstrained fingerprint, stationary evidence, or a position cycle stops that loop and retains the existing bounded verified scan. Fingerprint evidence never completes alignment: signed fine-yaw refinement and the three independently rendered full-resolution goal frames remain authoritative. After two normal macro runs observe the same stabilized load-in fingerprint, a device-local shortcut can apply one learned relative mouse drag and verify the goal across three frames; any mismatch falls back to the complete atlas path, repeated failures relearn the shortcut, and manual Auto Align neither trains nor consumes it. Thumbnail atlas lookup retains registered structural reranking so adjacent or visually aliased yaw remains distinct. Full-resolution goal verification may accept a larger vertical projection shift only when at least three of the four saved regions independently agree on the same translation; after any complete arrow-key turn and return, the engine re-observes the live pose before applying its saved fine correction. Playback and alignment apply the model's recorded client size. When the app or a workflow resizes Roblox, it leaves Roblox at that standardized client size so later detection and placement steps share the same geometry. Window discovery verifies the owning Roblox player process and carries its PID into run diagnostics. A stale handle is rediscovered after focus failure and transparently aliased for later capture and input. Normal framed sizing remains the first path; if Windows clamps it above the canonical client size, the Windows layer removes minimum-tracking frame styles, applies a verified borderless size, and retains the original styles for lifecycle cleanup.

Fast no align is a separate camera-preparation strategy and the default workflow. It standardizes the client, clamps zoom and top-down pitch with temporary Shift Lock, and sends no horizontal mouse or arrow input. One shared operation session records the prepared Roblox PID. Repeated matches and post-match mode changes reuse that pose; a verified Lobby observation, a different Roblox PID, or a new top-level macro operation invalidates it. Placement Setup owns deterministic category fallbacks and exact route overrides, including each setup's Team, delay between placements, default delay for newly authored After Start points, and every placement phase/offset/targeting priority. Changing that default preserves independently tuned offsets. All Expedition maps may fall back to the Expeditions category; Story Acts, Infinite, Mastery, and Challenge may fall back to their matching Story-map category. Runtime and export resolve the exact route first, then its category. Raid acts remain exact-only. Macro tasks own route policy such as Challenge types, difficulty, extraction, boss count, Hard mode, retry count, and completion target. The authoring collection is normalized into one stable Before Start group followed by one stable After Start group when loaded, edited, or saved. Drag handles and arrow actions reorder only within a phase, so an editor gesture cannot move an After Start action ahead of Start. The editor preserves canonical 808-by-611 placement coordinates while offering 50–200 percent visual zoom, cursor-centered wheel zoom, and middle-button viewport panning. The schedule orders placement offsets while preserving author order for ties, continues terminal/recovery detection between steps, and never sends a placement over a terminal or recovery candidate. Playback selects the configured unit, cancels it, then taps that slot three times to force a deterministic select/deselect/reselect state without parking. Each of up to eight click attempts positions the cursor 50 client pixels from the target, moves into the coordinate over 200 milliseconds through acknowledged motion, and clicks once. It never restarts the key/cancel normalization for that placement. Two consecutive frames must then contain both the fixed red selected-unit Close control and blue initial Priority/First control. A confirmed placement receives zero through eight configured targeting-key taps and only then may the cursor park between units. Authoring and runtime validation require every pair of Fast points to remain at least 7 client pixels apart. Runtime validation also rejects an unrelated category or route and rejects mixing Fast and learned-camera placement strategies. A versioned Fast share bundle serializes one plan plus the resolved setup graph as compressed JSON represented by Base64 text; it strips progress and cannot contain application settings, secrets, diagnostics, or camera models.

The workflow never reads Roblox memory or injects into the process. It observes screen pixels and emits ordinary Windows keyboard and mouse input. Before each top-level operation, the app resolves the verified Roblox HWND to its current monitor and requires 96-by-96 effective DPI (100% Windows display scale). Windows focus revalidates the same invariant, covering a replaced Roblox process or a monitor change during a long operation. A mismatched scale stops before keyboard or mouse input with a setup-specific message; the app never changes the Windows display setting itself.

Detector captures target the Roblox HWND through Windows Graphics Capture rather than copying the desktop rectangle at the same coordinates. Occluding applications are therefore excluded. The capture frame pool uses `R16G16B16A16_FLOAT`; linear scRGB pixels are locally tone-mapped and sRGB-encoded before becoming the same 8-bit `ImageFrame` consumed by vision. SDR pixels below the highlight shoulder preserve the standard transfer curve, while HDR/Auto HDR highlights are compressed instead of clipped. Desktop GDI capture remains limited to the user-driven camera-region selection overlay.

Frame-arrival callbacks remain notification-only for Windows 10 compatibility. The serialized capture path drains any queued compositor frames and scores only the newest one, so settled camera input cannot be compared against an older pose. If the post-barrier frame wait expires during a Roblox compositor handoff, the Windows layer disposes that capture session, creates one replacement with the longer initial-frame allowance, and retries without emitting any additional game input. A second timeout remains a session-level failure.

Hot-loop detection uses mode-owned active-state paths instead of exhaustively scoring unrelated navigation states. Challenge, Story/Raid, and Event monitors evaluate only their terminal and shared-selector states; Expedition gameplay scores its owned active states plus the root AFK, Disconnect, and Lobby recovery states. A frame-scoped weak cache shares exact configured-state, adaptive-state, and action-component results only while that captured `ImageFrame` remains alive. Production capture returns a fresh frame for each observation, and workflow/detector code must treat its pixel buffer as read-only after construction. Specialized detectors short-circuit legacy template work when the specialized result is authoritative. Deep Debug capture call-site stack traces are constructed only while a session is active. The Debug performance benchmark measures capture, mode detection, root recovery, and total work independently; exact corpus-equivalence tests protect every optimized state score and selected state.

Every top-level Macro plan can begin with a default-on fresh-session reset through the configured private server. That reset closes only a verified Roblox player PID when one is open, launches the normalized `roblox://` target, and waits for three stable Lobby observations before the one operation-scoped startup preflight begins. It runs exactly once per user-started plan, not between scheduled tasks or again after runtime recovery. Disabling it retains the existing clean-Lobby start requirement. The preflight first standardizes the Roblox client and—when the default-on game-settings check is enabled—temporarily enables the configured Shift Lock, clamps only the camera pitch to the straight-down limit, and restores Shift Lock without changing zoom or yaw. This removes background world interactables from the accessibility focus route before the preflight opens the in-game Settings panel from any fully loaded game state. It then normalizes UI Scale before attempting scale-dependent Lobby recognition, closes Settings through a reset accessibility-navigation sequence, requires three consecutive clean Lobby detections, reopens Settings the same way, and corrects the required game profile. Vision owns structural panel scale, selected-page, toggle-state, and Units-scrollbar detection. Automation owns the bounded sequence: use physical accessibility-navigation scan codes to enter an initial numeric UI Scale, measure the resulting rendered panel, and apply reciprocal feedback corrections within the game's 0.80–1.20 range until the rendered scale—not a device-dependent numeric value—is canonical. Only then may it visit Gameplay, Graphics, Units, and Misc and correct independently recognized toggles, including disabling the current Event Theme setting. The standalone Debug UI Scale and game-settings actions use the same pitch-only preparation; UI Scale stops after verified panel closure and therefore does not require Lobby. Settings-panel detection requires dark panel structure in addition to the red Close component, so a red Event-theme Lobby cannot impersonate an open panel before the profile has disabled that theme. Unknown controls remain hard compatibility failures. A missing/changed Roblox window, moving panel geometry, ignored action, unstable Lobby, or other verified UI/session failure may enter private-server recovery before task input begins. An initial preflight that never completed may retry after recovery; once it succeeds, ordinary Lobby returns and private-server restarts within that macro operation do not rerun it. Deep Debug sees the same captures and physical key/mouse events through the shared automation boundary.

Play navigation uses a separately configured A-Z key matching Anime Expeditions' **Toggle Play Menu** binding. The runner presses it from the lobby, terminal, or prestart state, verifies the expected selector or party preview, and retries boundedly; it does not depend on the position or visibility of either on-screen Play button.

Actionable navigation waits combine state stability with geometry stability. A detector-owned action must keep the same state and remain within three client pixels for at least two consecutive observations before input; a single late Play frame never bypasses that waiter. Unit Team loading anchors neutral-gray thumb candidates to the detected panel Close control, rejects candidates outside the field-observed scrollbar-thumb height, waits for the real thumb to stop moving, and uses over-travel at the top and bottom boundaries so Roblox clamps the thumb before the selected row is verified.

Macro plans persist immutable task definitions separately from per-task progress. The scheduler selects the lowest priority number among enabled, incomplete, and currently eligible tasks. A runner owns Roblox input until it returns a result; only then does the scheduler persist progress and choose again. Challenge tasks remain recurring and carry a next-eligible timestamp, while Expedition, Story, Raid, and Event tasks complete against saved victory or Infinite-runtime targets. An optional contiguous loop range can repeat its enabled finite tasks for a bounded number of total runs or forever; tasks before and after the range remain one-shot. Per-run victory/runtime baselines reset only the loop target calculation, while lifetime victories, defeats, and runtime remain monotonic. One operation-scoped reporting accumulator owns those totals across every task, loop, mode handoff, and process-recovery retry; individual result cards retain the runtime for that specific match. The outer recovering scheduler does not mutate task progress for a failed attempt. When enabled, it classifies session-level failures, asks the Windows process adapter to close only the verified Roblox PID, relaunches a normalized private-server URI through the registered Windows protocol, and holds scheduler control until the new canonical client produces three consecutive Lobby detections. Only then does it reload the saved plan and retry the same incomplete task. A three-restarts-per-ten-minutes circuit breaker bounds this process-level fallback.

Bounded match watchdogs use the same process-recovery path. Story Act/Mastery, Raid, Challenge, and Villain Invasion Event Acts 1–3 have a 12-minute terminal deadline; 25-wave Event Act 4 has a 17-minute deadline; Story Infinite is unbounded. Checkpoint-extracting Expeditions use 10 minutes for a zero-boss target or 15 minutes per positive boss target, while extraction-disabled runs are unbounded. A watchdog timeout is diagnostic/recovery state, never persisted match progress.

Scheduled mode handoffs use shared, verified navigation screens rather than leaving an owner-specific panel for the next runner. Challenge may retain its selector only between immediately consecutive Challenge matches; once the rotation enters cooldown, it closes that selector and verifies the game-mode selector before returning. Scheduled Expeditions returns at a verified Play party preview, which every normal mode entry can convert to the game-mode selector. Story and Raid return at the verified game-mode selector after both terminal results and recoverable camera-alignment skips. Event may hand off to a normal route through Play, but normal-to-Event and Event-to-Event handoffs return to a verified Lobby because Event is not represented in Play. If a handoff cannot be verified after bounded retries, the runner never starts another mode from an unknown screen: it raises a typed UI/session failure so an enabled private-server recovery can save diagnostics, relaunch, and retry the same incomplete task without repeating a preflight that already succeeded.

Runtime recovery is type-driven rather than message-driven. `RobloxSessionUnavailableException`, `RobloxUiUnavailableException`, navigation `TimeoutException`, capture `Win32Exception`, and an unrendered camera world are restart candidates. Model/plan validation, unsupported detector coverage, `PlayMenuBindingException`, malformed private-server input, cancellation, and internal state-machine invariants are hard stops. Automatic diagnostics run before the process closes. The circuit breaker permits at most three restarts in ten minutes; exhaustion is intentionally terminal. If no valid private-server target is enabled, a restart candidate propagates because the app has no safe rejoin destination.

Long-running gameplay monitors and Challenge cooldown waits schedule an ordinary `O` pulse every eight minutes through the shared focused-keyboard path. Input failures defer the next attempt for one minute without terminating the run. After an AFK-Chamber Return-to-Lobby action, Story/Raid navigation suppresses Play-key attempts throughout the teleport/loading interval and resumes only from a verified lobby or game-mode selector.

Story and Raid navigation uses specialized structural detectors for the mode selector, map selector, detail panel, party preview, prestart, terminal screens, and saved-team dialogs. Mode-detail detection treats **Enter Matchmaking** as optional because fresh lobby parties expose it while post-match parties retain only **Select Stage**; actions always map through the detected live button. Detail classification combines the stable accent header/edge and dark panel body with that independent live action rather than requiring the decorative Close circle to remain visually disconnected from the panel border. A launch-ready party is capability-based: both the lobby **Disband** family and post-match **Change Gamemode** family are accepted only when a live **Start** action is independently detected, while handoff logic continues to distinguish their different exit controls. Team loading is a separate service that validates the canonical client size before every capture and action. It detects and holds the neutral gray Unit Teams scrollbar thumb, drags the requested row into a field-confirmed aligned position, and verifies a fully visible Load button before clicking; relative wheel input remains available for other bounded list navigation.

The compiled `reward` state and its **Select Upgrade** action are owned exclusively by the Expedition runner. Challenge, Story, and Raid use their specialized terminal and navigation detectors and never classify, wait for, or click an Expedition reward card. A complete reward overlay remains negative cross-mode evidence for the shared Start-dialog geometry because Roblox can leave the underlying button visibly rendered but non-interactive.

Deep debug logging decorates the shared `IRobloxAutomation` boundary and the exclusive operation coordinator. Every frame returned to workflow or detector code is retained. Each high-level input action also takes a synchronous best-effort Roblox-client capture immediately before input and after success, cancellation, or failure, so an input-heavy interval cannot appear as an unexplained multi-second frame gap. These boundary captures use the undecorated automation backend to avoid recursive tracing; exact low-level key/mouse events still come from the Windows implementation. The vision layer emits detector scores and selected states, and the app forwards workflow progress and decisions. A bounded writer preserves ordering and applies backpressure rather than dropping frames. Each enabled operation snapshots a secret-free configuration graph and finalizes its own Zip64-capable archive for success, cancellation, or failure; if finalization fails, its staging directory is intentionally retained. One archive-text owner redacts webhook/private-server secrets, Discord user IDs, and the active Windows username/profile path from serialized events, logs, errors, and copied text model/configuration files before they enter that archive.

The optional Debug workspace wraps that same automation boundary with a checkpoint controller. It retains the newest captured frame, records detector and action checkpoints, and may gate either input actions or every detector observation. A gate only delays the owning operation; it never synthesizes an undo. Timeline rewind changes the WPF preview selection, while Step releases exactly the current live gate and Run removes subsequent gates. Debug navigation calls mode-owned navigation entry points and stops at verified prestart, team testing calls the production saved-team service, and **Teleport to lobby** calls the production lobby navigator: accessibility navigation opens the Back-to-Lobby confirmation, then it is disabled before the detector-owned red confirmation action is mouse-clicked and the final Lobby is verified. This prevents accessibility focus from moving controls behind the modal and keeps diagnostic tools out of separate blind-click implementations. The configurable key-press utility rejects the registered macro hotkey, resolves a supported Windows virtual key to a physical scan code, and enters the coordinator's Armed state until the global hotkey starts it. Its bounded held-key path focuses Roblox immediately before input and emits key-up from guaranteed cleanup on success, cancellation, or failure. The **Fast no align** utility delegates to the shared camera-pose preparation service: it standardizes the client, clamps zoom, temporarily enables Shift Lock for vertical camera drags, clamps top-down pitch, restores Shift Lock, and sends no yaw input. The performance benchmark runs one selected production detector path through the exclusive coordinator and reports separate average/p95 capture, mode-detection, root-recovery, and total-work timing without changing detector thresholds. The experimental resource-refuel tool is deliberately Debug-only: it calibrates and exercises a field-observed Areas/Hub/blind-route sequence but is not exposed to Macro plans, scheduling, or automatic eight-hour timing. Debug operation context, checkpoints, frames, detections, and inputs flow through the existing Deep Debug archive when enabled.

Camera readiness is a separate pre-alignment gate over the saved world regions. It rejects the field-confirmed textureless blue load state before any yaw or unit placement. Mode runners first perform their verified in-client Play/navigation recovery and retry the same route; a resulting bounded timeout may then reach the outer process-restart policy. Fine-yaw movement is decomposed into identical atomic right-drag gestures, so calibration and runtime correction do not mix one multi-pixel gesture with repeated one-pixel gestures on devices where Roblox consumes those paths differently.
