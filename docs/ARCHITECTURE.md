# Architecture

The application separates reusable automation behavior from the WPF shell:

The Macro Plan Delete action is available only for a saved plan. It confirms the destructive action, flushes pending autosave, removes the requested plan file, selects and persists the next saved plan deterministically, and returns to a clean unsaved plan when none remain.

```text
Core <- Vision ----\
  ^                 \
  +---- Windows -----> Automation -> App
  +-------------------------------> App
```

Project references are allowlisted and checked by `scripts/Test-RepositoryPolicy.ps1`. Adding a project or dependency requires an explicit architecture-policy update; lower layers must never acquire a reference to a higher layer.

- `ExpeditionsMacro.Core` contains immutable geometry, image, model, preset, persistence, and workflow contracts.
- `ExpeditionsMacro.Windows` owns Win32 window discovery, per-monitor effective-DPI validation, exact client sizing, Windows Graphics Capture of the Roblox compositor surface, verified Dashboard window pinning, FP16 scRGB-to-SDR conversion, DPAPI, configurable key input, Roblox-compatible mouse nudging and acknowledged client-control drags, Roblox `O`-key zoom with a wheel fallback, and vertical camera-pitch input. The global hotkey accepts safe single-key letters, digits, punctuation, numpad keys, and supported function keys. Shift Lock resolves the saved virtual key to a physical scan code and preserves extended-key identity, so Left/Right Shift and Left/Right Ctrl remain distinct.
- `ExpeditionsMacro.Vision` owns lighting-normalized scoring, temporal medians, detector-pack compilation, validation, classification, Expedition, Challenge, supported Event and Bounty Board states, Story/Raid stage navigation, saved-team dialogs, map and difficulty selection, node hues, hotbar checks, Bounty-number suffix recognition, and bounded wave-counter recognition.
- `ExpeditionsMacro.Automation` owns Fast camera-pose preparation, placement recording/playback, saved-team loading, the Expedition, Challenge, Story, Raid, supported Event, and Bounty runners, the prioritized Macro scheduler, recovery, Discord Components V2, and the application-update release/transport/session boundary.
- `ExpeditionsMacro.App` is the single WPF interface and exclusive input-owner coordinator. It presents update state and owns the two explicit user-consent boundaries, but it does not parse release metadata or validate downloads.
- `ExpeditionsMacro.DatasetBuilder` compiles a local capture corpus into a small, hashed detector pack.
- `ExpeditionsMacro.DetectorViewer` is a standalone WPF inspection and dataset-annotation tool over Vision's inspection catalog. It accepts images, recursive image folders, Deep Debug ZIPs, and the complete checkout `datasets` tree through a repository-aware source. Its filename-first frame picker keeps large corpora directly navigable. It overlays production-owned geometry and live actions and never owns Roblox input. Repository fixtures may be annotated with per-detector expected results, notes, and canonical regions in the atomically written `datasets/detector-annotations.json` manifest; those annotations are implementation guidance and never alter production decisions. The catalog records an explicit limitation when a production helper has no safe standalone inspection path.

Application updates are a separate non-input operation. Automation parses semantic versions, enforces the current stable/prerelease channel, validates the exact GitHub tag/release URL/four-asset inventory, follows a bounded HTTPS redirect allowlist, and requires GitHub's asset digest plus the downloaded checksum manifest to agree. Downloads use a `.partial` file under the app-owned local update directory and become persistent only after their declared size and SHA-256 match. Restart recovery rehashes the staged installer; a completed, stale, malformed, or tampered stage is removed. App starts the optional automatic metadata check, shows non-modal state, and requires one user action to download plus a second confirmation to open the ordinary installer. The running app never overwrites its own binaries, silently installs, polls, sends telemetry, or adds credentials to GitHub requests.

The WPF shell exposes one `MacroPage` runtime owner through two workspaces. **Dashboard** owns supervision and operation-scoped controls: the pinned Roblox client, start/stop, current run, log, reporting, reconnect, startup preparation, and key bindings. **Macro Plan** owns plan authoring, connected task blocks, loop configuration, and sharing. Both navigation entries resolve to the same page instance so scheduler state, counters, log ownership, and coordinator subscriptions cannot diverge. The Dashboard pins only a process-verified Roblox player HWND as a borderless top-level cutout over the 808-by-611 live-view slot. It neither reparents Roblox as a child nor assigns the WPF window as its owner: preserving independent top-level composition keeps Windows Graphics Capture producing fresh frames, lets direct mouse and keyboard interaction reach Roblox normally, and prevents an app crash from destroying the Roblox window. While the slot is visible, a watchdog temporarily keeps Roblox in the topmost band and follows Dashboard layout changes without activating it. Focus alone does not release the pin. The watchdog reads the foreground top-level window's DWM frame, with a `GetWindowRect` fallback, and suspends Roblox without minimizing only when a visible, non-minimized foreign window has positive-area overlap with the Dashboard. A focused window on another monitor, beside the Dashboard, or touching only its edge leaves the live view pinned; the pin can restore as soon as overlap clears even if that other application keeps focus. Before the app presents an owned modal error, it synchronously suspends the pin and holds a modal-depth guard until the dialog closes; the same ownership check remains a watchdog fallback. This ordering keeps modal errors and questions above Roblox instead of reacting after a topmost Roblox window has already covered them. Leaving Dashboard, scrolling the full live-view slot out of view, or minimizing the app removes the pin and minimizes Roblox without activating it; the original standalone styles and bounds remain retained so returning to the visible Dashboard can re-pin the same window. A manual Pin toggle-off or application shutdown instead restores the exact prior standalone styles, extended styles, bounds, and visible state, and neither path minimizes Roblox. Automatic utility minimization remains suppressed while pinning is requested so the Dashboard does not disappear from behind its cutout. Navigation and app shutdown remain blocked if the requested verified window transition fails. A replacement Roblox HWND is discovered and pinned after a relaunch.

All saved coordinates are relative to the canonical 808 by 611 Roblox client. Fast preparation is the sole executable camera-pose strategy: it standardizes the client, clamps zoom, snapshots the configured Shift Lock key for balanced enable/cleanup, clamps top-down pitch through vertical drags, restores Shift Lock, and sends no horizontal mouse or arrow input. One operation session records the prepared Roblox PID. Repeated matches and post-match mode changes reuse that pose; a verified Lobby observation, a different Roblox PID, or a new top-level macro operation invalidates it. Public-beta camera-model enum values, identifiers, and preset fields remain only so existing files can be deserialized and surfaced with migration guidance. They are not offered for new authoring and are rejected before Roblox discovery or input; this compatibility boundary is not runtime camera-model support.

When the app or a workflow resizes Roblox, it leaves Roblox at the standardized client size so later detection and placement share the same geometry. Window discovery verifies the owning Roblox player process and carries its PID into run diagnostics. A stale handle is rediscovered after focus failure and transparently aliased for later capture and input. Normal framed sizing remains the first path; if Windows clamps it above the canonical client size, the Windows layer removes minimum-tracking frame styles, applies a verified borderless size, and retains the original styles for lifecycle cleanup.

Placement Setup owns deterministic category fallbacks and exact route overrides, including each setup's Team, ordered Match Steps, targeting and Auto Upgrade actions, explicit delays, retry policy, and advanced timing overrides. All Expedition maps may fall back to the Expeditions category; Story Acts, Infinite, Mastery, and Challenge may fall back to their matching Story-map category. Runtime and export resolve the exact route first, then its category. Bounty's regular-Challenge leg deliberately uses the five required Story Infinite setups and converts each resolved setup to a Challenge-targeted in-memory record before the Challenge runner validates it; the persisted setup and share dependency remain Story-scoped. Raid acts remain exact-only. Villain Invasion Act 1's two deterministic spawn approaches are separate exact routes; the approach participates in placement compatibility and scheduler route identity so changing it forces a Lobby handoff instead of Repeat Stage. Macro tasks own route policy such as Challenge types, difficulty, extraction, boss count, Hard mode, retry count, and completion target. Every authoring collection contains exactly one required `StartGame` sentinel. Actions above it execute before the runner's verified Start action and actions below it execute afterward; users may reorder the sentinel but cannot add, edit, duplicate, or remove it. Legacy phase-based setups migrate deterministically by placing their before-Start rows above the sentinel and converting after-Start absolute offsets into explicit Delay steps below it, preserving author order for equal offsets. The editor preserves canonical 808-by-611 placement coordinates while offering 50–200 percent visual zoom, cursor-centered wheel zoom, and middle-button viewport panning. The scheduler continues terminal/recovery detection between actions and never sends placement input over a terminal or recovery candidate.

For a fallback-capable exact route in Step Mode, the required `StartGame` sentinel is structural and does not keep an otherwise empty override active. Removing the final user-authored action deletes that exact override through autosave, refreshes the catalog to its inherited state, and makes runtime and export resolve the category setup. Category setups and exact routes with a Recording Mode assignment remain configured. New Match Steps from either the action editor or placement map append at the bottom after Start Game; deliberate Before Start work requires explicit timeline reordering.

Match settings also persist the Targeting and Auto Upgrade defaults inherited by future Place actions. Applying new defaults never rewrites existing Match Steps. Setups written before these fields existed retain the established Target First and Auto Priority 1 authoring defaults.

Step Mode resolves both the user-configured Cancel Placement and Quick Placement physical keys before any Roblox input. For each contiguous placement batch in the ordered timeline, playback presses Cancel Placement once, holds Quick Placement across the batch, taps a unit slot only when it differs from the preceding row, and sends three complete clicks at each saved coordinate over exactly 50 milliseconds. It then releases Quick Placement, presses Cancel Placement again, and enters a separate verification/configuration pass in author order. Delay, reconfiguration, and upgrade actions create explicit timeline boundaries. Quick Placement and every mouse button are released on success, cancellation, or failure. Recording Mode and a Step Mode setup without placement actions do not require either binding.

The verification pass clicks each saved coordinate once, parks the cursor so a hover card cannot cover the selected-unit Close control, and requires two consecutive selected-unit-panel frames. A normally confirmed placement then receives zero through eight configured targeting-key taps followed by zero through six Auto Upgrade Unit taps for the step's configured priority, after which bounded safe-idle clicks prove the panel closed before playback advances. Each setup owns one through eight total placement attempts and defaults to one. The initial placement batch is attempt one; a higher setting re-places and rechecks only the failed row without replaying already confirmed rows. Exhausting selected-unit proof logs and skips only that row without targeting, Auto Upgrade, or successful-placement progress. Neither the placement service nor an Expedition runner may infer success from a visually empty hotbar slot because hover and scene changes can produce ambiguous occupancy evidence. Authoring and runtime validation require every pair of coordinate-owning Match Steps to remain at least 7 client pixels apart. Runtime validation also rejects an unrelated category or route. A versioned Fast share bundle serializes one plan plus the resolved setup graph as compressed JSON represented by Base64 text; it strips progress and cannot contain application settings, secrets, diagnostics, or retired camera-model data.

`PlacementPhase` and `DelayAfterStartMilliseconds` remain parse-only compatibility fields for older setup and share payloads. Current authoring derives their normalized values from the single Start Game boundary and writes explicit Delay actions; no phase selector, phase badge, or separately editable after-Start offset remains in the product surface.

Fast share schema 2 extends that dependency graph with every public-beta Expedition, Challenge, Story, or Raid preset referenced by the saved plan and the complete Fast placement setups those presets reference. Direct tasks still export the exact route override or resolved category fallback. Import saves placement dependencies, then presets, then the progress-free plan. Schema 1 direct-task bundles remain readable. Manual input recordings remain device-local: neither raw recording events nor recording references may enter a share bundle, and export stops clearly when a resolved setup uses **Recording Mode**. Returning it to **Step Mode** restores its preserved ordinary steps as the shareable dependency. Retired camera-model data, app-managed settings, secrets, diagnostics, and unrelated local data remain excluded.

Each placement step also owns an Auto Upgrade priority from Off through Priority 6. Newly authored steps default to Priority 1. The public beta.31 boolean representation remains readable: true migrates to Priority 1, while false or a missing legacy value migrates to Off; normalized saves and share bundles write the named priority. After selected-unit proof and targeting taps, playback sends the configured Auto Upgrade Unit key exactly zero through six times, without using a visual label as confirmation. Reconfigure actions retain the current Auto Upgrade state for each stable placement ID and cycle forward through Off and Priority 1 through Priority 6 using only the taps needed to reach the requested state; they never hold the key or normalize a known state first. Upgrade actions have a separate advanced readiness policy: the default path requires fresh selected-panel evidence, waits through the ordinary unaffordable gray control, accepts only two consecutive green controls before each keypress, and treats the wider gray Maxed control as a successful end to the remaining presses. The advanced direct-input opt-out sends the requested presses without panel or affordability proof. Startup settings normalization keeps the game's global Auto-Upgrade Placed Units option off so this per-step policy is authoritative.

The Priority 1 authoring default above is the setup fallback, not a forced value: a setup may choose any supported Targeting and Auto Upgrade defaults for later Place actions. A missing legacy per-step Auto Upgrade value still loads as Off.

The optional manual-input route is a separate Fast execution strategy. Core owns its versioned client-relative event schema and atomic local repository; Windows owns physical low-level hooks, scan-code and mouse serialization, acknowledged initial pointer positioning, absolute-timeline scheduling, `SendInput`, focus/geometry checks, and held-input cleanup; Automation resolves the selected recording and substitutes it for Start plus placement playback only after the mode runner has positively verified prestart; App exposes recording and assignment through the same exclusive operation coordinator. Recording buffers keyboard and mouse hook observations together, orders them by their wrap-safe native Windows timestamp, and preserves callback sequence only for events in the same native millisecond. Before saving, a button or wheel coordinate one pixel from the ordered path becomes an explicit persisted mouse-move event at that action coordinate; a larger unresolved gap fails capture instead of producing an unreplayable recording. After validation, focus, geometry, and pointer preflight complete, the absolute playback loop runs on a dedicated non-thread-pool timing worker. Its timing-critical target checks use direct uninstrumented Win32 probes rather than synchronous diagnostic wrappers. Every event is checked before and after injection against its absolute offset. Signed drift within +/- 50 milliseconds is the timing-quality target; playback continues without shifting any future deadline while drift remains below the +/- 2,000-millisecond hard stop. This remains a per-event absolute-timeline check, so timing error never accumulates through chained relative delays. Before a button or wheel event, the real pointer may differ from its recorded client-relative coordinate by at most one pixel on either axis; larger drift stops playback, while this integer-rounding tolerance never moves the pointer or invents a missing motion event. No detector or other workflow call may run while the recording owns input. Raw recording events are excluded from Deep Debug and Fast share codes.

The workflow never reads Roblox memory or injects into the process. It observes screen pixels and emits ordinary Windows keyboard and mouse input. Before each top-level operation, the app resolves the verified Roblox HWND to its current monitor and requires 96-by-96 effective DPI (100% Windows display scale). Windows focus revalidates the same invariant, covering a replaced Roblox process or a monitor change during a long operation. A mismatched scale stops before keyboard or mouse input with a setup-specific message; the app never changes the Windows display setting itself.

Detector captures target the Roblox HWND through Windows Graphics Capture rather than copying the desktop rectangle at the same coordinates. Occluding applications are therefore excluded. The capture frame pool uses `R16G16B16A16_FLOAT`; linear scRGB pixels are locally tone-mapped and sRGB-encoded before becoming the same 8-bit `ImageFrame` consumed by vision. SDR pixels below the highlight shoulder preserve the standard transfer curve, while HDR/Auto HDR highlights are compressed instead of clipped.

Frame-arrival callbacks remain notification-only for Windows 10 compatibility. The serialized capture path drains any queued compositor frames and scores only the newest one, so settled input cannot be compared against an older UI state. If the post-barrier frame wait expires during a Roblox compositor handoff, the Windows layer disposes that capture session, creates one replacement with the longer initial-frame allowance, and retries without emitting any additional game input. A second timeout remains a session-level failure.

Hot-loop detection uses mode-owned active-state paths instead of exhaustively scoring unrelated navigation states. Challenge, Story/Raid, and Event monitors evaluate only their terminal and shared-selector states; Expedition gameplay scores its owned active states plus the root AFK, Disconnect, and Lobby recovery states. Bounty Board navigation evaluates only its owned board, reroll-confirmation, insufficient-Gold, card-action, and number-suffix evidence; Infinite Bounty gameplay adds only its bounded wave objective to the existing Stage monitor. Bounty-number recognition evaluates exact embedded `#1` through `#10` templates first, then may use a small in-process glyph-similarity fallback inside the same action-owned title window. That fallback retains an explicit similarity floor, runner-up margin, and reviewed position bound; it is not a general OCR runtime, and its result cannot own a card or authorize input by itself. A frame-scoped weak cache shares exact configured-state, adaptive-state, and action-component results only while that captured `ImageFrame` remains alive. Production capture returns a fresh frame for each observation, and workflow/detector code must treat its pixel buffer as read-only after construction. Specialized detectors short-circuit legacy template work when the specialized result is authoritative. Deep Debug capture call-site stack traces are constructed only while a session is active. The Debug performance benchmark measures capture, mode detection, root recovery, and total work independently; exact corpus-equivalence tests protect every optimized state score and selected state.

The two private-server restart checkboxes persist immediately through the serialized settings store. Page navigation reloads only those saved values; a failed write restores the last saved state and reports the failure beside the reconnect controls.

Every top-level Macro plan can begin with a default-on fresh-session reset through the configured private server. That reset closes only a verified Roblox player PID when one is open, launches the normalized `roblox://` target, standardizes the new client to 808 by 611, and waits for three stable startup observations before the one operation-scoped preflight begins. Exact Lobby is accepted; a startup-only fallback also accepts an otherwise unclassified Lobby-shaped view whose raw Lobby evidence is within five percentage points of its normal threshold and remains at least twenty percentage points stronger than every competing state. This fallback authorizes preflight only, allowing enabled UI Scale correction to run before strict Lobby recognition; the preflight must still prove three clean Lobby frames before any task input. When process recovery is configured, a recoverable failure before preflight completion may relaunch through the same startup gate; after successful preflight, runtime process recovery retains the strict three-Lobby-frame gate and never uses the startup fallback. The reset runs exactly once per user-started plan, not between scheduled tasks or again after runtime recovery. Disabling it retains the existing clean-Lobby start requirement. The preflight first standardizes the Roblox client. UI Scale correction and required game-settings correction are independent default-on responsibilities. Either enabled responsibility temporarily enables the configured Shift Lock, clamps only camera pitch to the straight-down limit, and restores Shift Lock without changing zoom or yaw. The UI Scale responsibility opens Settings, directly measures the settled panel, accepts the inclusive rendered range from 0.98 through 1.02, and corrects only values outside that range. Vision detects the opaque Roblox Settings gear at either fixed top-bar offset without inspecting or depending on the optional microphone/headset control. Both offsets accept the field-observed normal and high-contrast opaque gear outlines while retaining the same structural bounds, selected-state distinction, and fixed action ownership. Vision also owns the selected page, scale-aware Misc action, UI Scale input structure, structural panel scale, toggle state, and Units scrollbar. Automation requires two stable gear observations, clicks that same detected gear through acknowledged client-relative motion to open and close Settings, verifies the filled or outline gear together with the Settings-panel transition, never clicks the red panel Close control, and requires stable detected click geometry before selecting Misc or the input. It waits 2.5 seconds after the verified input click without treating the cyan accessibility-selection ring as text-focus evidence, enters an initial numeric UI Scale through ordinary physical key input, measures the resulting rendered panel, and applies reciprocal feedback corrections within the game's 0.80–1.20 range until the rendered scale, not a device-dependent numeric value, is canonical. The required-settings responsibility separately opens Settings after three consecutive clean Lobby detections and corrects the required Gameplay, Graphics, Units, and Misc toggles, including disabling the current Event Theme setting. It never types or changes UI Scale; if its direct panel measurement is noncanonical while UI Scale correction is disabled, it closes Settings and stops with guidance to enable the separate UI Scale check. Disabling UI Scale correction skips scale measurement entirely; no Lobby-scene scale estimate is used. Disabling both responsibilities sends no camera or Settings input and retains only the stable-Lobby gate. The standalone Debug UI Scale and game-settings actions retain the active pitch/open/correct/close behavior; UI Scale stops after verified panel closure and therefore does not require Lobby. Settings-panel detection requires the scale-aware complete page rail—one cyan selected page plus repeated neutral unselected controls—in addition to the red Close component; variable page-body brightness is not ownership evidence. This rejects the red Event-theme Lobby and structurally similar Areas Lobby before any control action. Unknown controls remain hard compatibility failures. A missing/changed Roblox window, moving panel geometry, ignored action, unstable Lobby, or other verified UI/session failure may enter private-server recovery before task input begins. An initial preflight that never completed may retry after recovery; once it succeeds, ordinary Lobby returns and private-server restarts within that macro operation do not rerun it. Deep Debug sees the same captures and physical key/mouse events through the shared automation boundary.

Roblox chat normalization is a separate fixed-top-bar responsibility. Vision classifies the outlined closed-chat glyph and the opaque filled open-chat glyph inside the canonical button centered at `(139, 34)`; it does not inspect the optional microphone or headset slot and does not scale the action with Anime Expeditions UI Scale. Automation requires two consecutive matching observations before acting. A verified closed indicator authorizes no input; a verified open indicator authorizes only the detected chat-button click, after which two fresh closed observations are required. An ignored click may be retried once. Unknown or unstable evidence never authorizes input and exits through the existing typed UI-unavailable path. This normalizer runs after Lobby acquisition and again at match prestart before Settings, placement, or manual-recording ownership, so chat text cannot cover detector regions or receive gameplay keys.

Play navigation uses a separately configured A-Z key matching Anime Expeditions' **Toggle Play Menu** binding. The runner presses it from the lobby, terminal, or prestart state, verifies the expected selector or party preview, and retries boundedly; it does not depend on the position or visibility of either on-screen Play button. Story/Raid handoff accepts consecutive bundled `play` observations as shared-selector proof when the specialized Stage detector returns no owned state, covering accounts whose locked mode tile is dim, but it never lets that fallback override a recognized Stage state or trigger input before stability.

Event navigation gives the shifted Act selector precedence over Event Home. The selected Villain Invasion sidebar may remain visible on both screens, so Act-selector ownership additionally requires the full-width selector rail and its opaque subtitle before the Event Home proof is considered. Event Home remains owned by the selected Villain Invasion card and live Event Gamemode action; decorative header artwork may finish rendering later and is not required.

Every owned UI wait is observation-aware, including startup, recovery, Lobby, Match Lobby, Settings, Play, Stage, Challenge, Event, Expedition, Team, Refuel, and placement confirmation. A detector-owned action must keep the same state and remain within three client pixels for at least two consecutive observations before input; a single late frame never bypasses that waiter. Budgets seed state already captured by the caller and guarantee enough completed fresh observations for the requested stability count even when one detector pass is slower than its nominal soft timeout. Each original hard deadline, click limit, drag limit, and retry cap remains independently bounded, so slower observation cannot multiply physical input or turn a missing state into an indefinite wait. A detector action is accepted only from current live state-owned geometry; a manifest coordinate or other static fallback never authorizes input. Unit Team loading anchors neutral-gray thumb candidates to the detected panel Close control, rejects candidates outside the field-observed scrollbar-thumb height, waits for the real thumb to stop moving, and uses over-travel at the top and bottom boundaries so Roblox clamps the thumb before the selected row is verified.

Macro plans persist immutable task definitions separately from per-task progress. Every task present in a plan is active; users remove work that should no longer run. Public-beta `enabled` JSON fields remain readable but are discarded, and normalized plans and share codes omit them. Macro Plan and Placement Setup authoring persist every committed edit automatically through serialized, versioned save lifecycles. An active save drains edits queued behind it; plan rename saves retain the source identifier and original replacement ancestry captured with that edit; switching, execution, export, deletion, navigation, and shutdown flush the relevant queued and in-flight work. Load-driven UI synchronization does not enqueue saves, stale completions cannot replace a newer status, and failed writes remain visibly retryable. The scheduler selects the lowest priority number among incomplete and currently eligible tasks. A runner owns Roblox input until it returns a result; only then does the scheduler persist ordinary result progress and choose again. Challenge and Utility tasks remain recurring and carry a next-eligible timestamp. Challenge results also retain their current reset epoch, attempted types, and daily-limit evidence. A combined refuel Utility atomically checkpoints its first verified station before continuing to the second; this checkpoint save completes even when Stop is requested immediately afterward. A refuel Utility is initially eligible, records its next due time from successful completion, and is treated as complete for the current loop pass while that timestamp is in the future; Expedition, Story, Raid, and Event tasks complete against saved victory or Infinite-runtime targets. Resetting plan progress removes recurring-task checkpoints together with ordinary counters and due times. A plan may contain multiple finite loop blocks plus at most one Forever block. Loop ranges form a laminar hierarchy: they may be separate or fully nested, including a finite block nested across the same task range as an outer Forever block, but may never cross. A Forever block may begin at any task but must end at the plan's final task. Each inner loop completes all of its configured runs for every containing-loop iteration; repeating an outer loop resets its descendant loop progress and only the per-run task baselines inside that range. Lifetime victories, defeats, and runtime remain monotonic. Beta 29's single-loop fields remain readable and migrate to the multi-loop collection when the scheduler next saves the plan. The Macro Plan editor starts with no loop control enabled; **Add loop block** creates a removable block, and nested blocks are ordered and indented inside their containing range. One operation-scoped reporting accumulator owns totals across every task, loop, mode handoff, and process-recovery retry; individual result cards retain the runtime for that specific match. The outer recovering scheduler does not mutate task progress for a failed attempt. When enabled, it classifies session-level failures, asks the Windows process adapter to close only the verified Roblox PID, relaunches a normalized private-server URI through the registered Windows protocol, and holds scheduler control until the new canonical client produces three consecutive Lobby detections. Only then does it reload the saved plan and retry the same incomplete task. A ten-restarts-per-ten-minutes circuit breaker bounds this process-level fallback.

Bounded match watchdogs use the same process-recovery path. Story Act/Mastery, Raid, Challenge, and Villain Invasion Event Acts 1–3 have a 12-minute terminal deadline; 25-wave Event Act 4 has a 17-minute deadline; Story Infinite is unbounded. Checkpoint-extracting Expeditions use 10 minutes for a zero-boss target or 15 minutes per positive boss target, while extraction-disabled runs are unbounded. A watchdog timeout is diagnostic/recovery state, never persisted match progress.

Scheduled mode handoffs use shared, verified navigation screens rather than leaving an owner-specific panel for the next runner. Challenge may retain its selector only between immediately consecutive Challenge matches; once the rotation enters cooldown, it closes that selector and verifies the game-mode selector before returning. Scheduled Expeditions returns at a verified Play party preview, which every normal mode entry can convert to the game-mode selector. Story and Raid return at the verified game-mode selector after terminal results and recoverable UI/session failures. Event may hand off to a normal route through Play, but normal-to-Event and Event-to-Event handoffs return to a verified Lobby because Event is not represented in Play. If a handoff cannot be verified after bounded retries, the runner never starts another mode from an unknown screen: it raises a typed UI/session failure so an enabled private-server recovery can save diagnostics, relaunch, and retry the same incomplete task without repeating a preflight that already succeeded.

Runtime recovery is type-driven rather than message-driven. `RobloxSessionUnavailableException`, `RobloxUiUnavailableException`, navigation `TimeoutException`, and capture `Win32Exception` are restart candidates. Model/plan validation, retired camera-model execution, unsupported detector coverage, `PlayMenuBindingException`, malformed private-server input, cancellation, internal state-machine invariants, and `ManualInputPlaybackTimingException` are hard stops. A playback timing miss is local scheduling evidence that restarting Roblox cannot correct, so it reports the signed drift and event boundary without consuming the restart circuit. Automatic diagnostics run before the process closes. The circuit breaker permits at most ten restarts in ten minutes; exhaustion is intentionally terminal. If no valid private-server target is enabled, a restart candidate propagates because the app has no safe rejoin destination.

Long-running gameplay monitors and Challenge cooldown waits schedule an ordinary `O` pulse every eight minutes through the shared focused-keyboard path. Input failures defer the next attempt for one minute without terminating the run. After an AFK-Chamber Return-to-Lobby action, Story/Raid navigation suppresses Play-key attempts throughout the teleport/loading interval and resumes only from a verified lobby or game-mode selector.

Story and Raid navigation uses specialized structural detectors for the mode selector, map selector, detail panel, party preview, prestart, terminal screens, and saved-team dialogs. Mode-detail detection treats **Enter Matchmaking** as optional because fresh lobby parties expose it while post-match parties retain only **Select Stage**; actions always map through the detected live button. Detail classification combines the stable accent header/edge and dark panel body with that independent live action rather than requiring the decorative Close circle to remain visually disconnected from the panel border. A launch-ready party is capability-based: both the lobby **Disband** family and post-match **Change Gamemode** family are accepted only when a live **Start** action is independently detected, while handoff logic continues to distinguish their different exit controls. Team loading is a separate service that validates the canonical client size before every capture and action. It anchors the neutral gray Unit Teams scrollbar thumb to a bounded Team-list Close band, maps the stable thumb to the first visible Team, accepts any complete requested Load button in the three-row viewport, and drags only when that requested row is not already fully visible; relative wheel input remains available for other bounded list navigation. One operation-scoped Team session remembers only a positively verified Team and its owning Roblox process, allowing later routes in the same user-started Macro to reuse it; a different Team, replaced process, stop, or new start invalidates that knowledge.

Every user-started Macro operation also owns one in-memory Team session. A runner records a configured Team only after the production load-confirmation transaction succeeds. Later Story, Raid, Event, Challenge, Expedition, and Bounty routes may seed their repeated-route preparation state from that session only when both the requested Team and Roblox process identity match. Before any required switch, the session becomes unknown; only a verified completion records the new Team. A failed or interrupted switch therefore cannot leave the previously remembered Team reusable after Roblox may already have changed. A replaced Roblox process also invalidates the session. The session is never persisted, shared, or reused after a stop/new start.

The compiled `reward` state and its **Select Upgrade** action are owned exclusively by the Expedition runner. Challenge, Story, and Raid use their specialized terminal and navigation detectors and never classify, wait for, or click an Expedition reward card. A complete reward overlay remains negative cross-mode evidence for the shared Start-dialog geometry because Roblox can leave the underlying button visibly rendered but non-interactive.

Bounty is a recurring scheduler task. It remains eligible while board or objective work can advance, waits for the next ordinary Challenge reset when a conditional card is cooldown-blocked, and waits for the next UTC day after ten claims. Insufficient reroll Gold places only Bounty in an operation-scoped exclusion set; active viable objectives finish first, lower-priority tasks continue, and the exclusion disappears on the next user-started Macro operation.

Bounty progress has a separate device-local repository because it represents the board state of the one Roblox account assumed per Windows user rather than ordinary loop progress. The record stores the UTC day, claimed count, unique Bounty numbers whose claimed cards settled dimmed that day, active unique Bounty numbers, and deterministic objective counters. Every user-started Macro operation creates one Bounty operation session. Its first Bounty selection processes the live board—including claims and policy-owned rerolls—before stale local active entries can authorize route work, even when those entries appear executable. The session is marked reconciled only after the resulting state is saved, so recovery retries an interrupted initial transaction but does not repeat a completed one. A UTC-day advance resets both the claim count and dimmed-number exclusion set. Bounty always rerolls non-viable Mythics with a fixed parking limit of zero; the former task field is deserialize-only compatibility and normalized plans omit it. Share bundles include the six deterministic Placement Setup dependencies, but never include account-local Bounty state.

Board capacity is derived from stable live yellow **Reroll** and green **Claim** actions after one bounded horizontal scroll; cards with neither action are non-actionable regardless of position. The public beta.45 through beta.47 Bounty schema is intentionally reset because Bounty 2 used the wrong Flower/Fairy route identity and the user confirmed that no deployed Bounty state requires preservation; translating the incorrect Fairy King Forest key would falsely preserve Flower Forest progress.

Equal-card-count left/right Bounty action interpretations use the lower total bounded column distance, so a gold pin glyph aligned to the opposite column family cannot suppress a more closely aligned live Reroll action.

Bounty begins from verified Lobby because the Event Bounty Board is not represented in Play. It returns through the verified in-match Lobby door after every objective route, continues remaining executable work after the successful initial transaction, and reopens the board when no executable work remains for claiming or reconciliation. Normal-to-Bounty and Bounty-to-any-mode handoffs therefore require verified Lobby rather than reusing an Event or Play surface.

Deep debug logging decorates the shared `IRobloxAutomation` boundary and the exclusive operation coordinator. Every frame returned to workflow or detector code receives a permanent ordered text record. Its PNG bytes remain only inside the operation's configured 1-through-120-minute rolling frame-image window; pruning an older PNG never removes its `events.jsonl` record, detector/state/action/input context, or sanitized run-log text. Each high-level input action also takes a synchronous best-effort Roblox-client capture immediately before input and after success, cancellation, or failure, so the retained tail explains the terminal boundary even during an input-heavy interval. These boundary captures use the undecorated automation backend to avoid recursive tracing; exact low-level key/mouse events still come from the Windows implementation. The vision layer emits detector scores and selected states, and the app forwards workflow progress and decisions. A bounded writer preserves ordering and applies backpressure rather than dropping text or in-window frames. Each enabled operation snapshots a secret-free configuration graph and finalizes its own Zip64-capable archive for success, cancellation, or failure; the manifest distinguishes total frame records from retained and discarded PNGs, and if finalization fails its staging directory is intentionally retained. One archive-text owner redacts webhook/private-server secrets, Discord user IDs, and the active Windows username/profile path from serialized events, logs, errors, and copied text model/configuration files before they enter that archive.

The optional Debug workspace wraps that same automation boundary with a checkpoint controller. It retains the newest captured frame, records detector and action checkpoints, and may gate either input actions or every detector observation. A gate only delays the owning operation; it never synthesizes an undo. Timeline rewind changes the WPF preview selection, while Step releases exactly the current live gate and Run removes subsequent gates. Debug navigation calls mode-owned navigation entry points and stops at verified prestart, team testing calls the production saved-team service, and **Teleport to lobby** calls the production lobby navigator: Vision requires the opaque door/arrow/handle structure at one of the two fixed top-bar offsets across consecutive captures, the shared acknowledged-motion path clicks that detected door, and only then may the existing detector-owned red confirmation action be mouse-clicked before final Lobby proof. The optional microphone or headset slot is ignored rather than classified. This keeps diagnostic tools out of separate blind-click or accessibility-navigation implementations. The configurable key-press utility rejects the registered macro hotkey, resolves a supported Windows virtual key to a physical scan code, and enters the coordinator's Armed state until the global hotkey starts it. Its bounded held-key path focuses Roblox immediately before input and emits key-up from guaranteed cleanup on success, cancellation, or failure. The **Fast no align** utility delegates to the sole camera-pose preparation service: it standardizes the client, clamps zoom, temporarily enables Shift Lock for vertical camera drags, clamps top-down pitch, restores Shift Lock, and sends no yaw input. The performance benchmark runs one selected production detector path through the exclusive coordinator and reports separate average/p95 capture, mode-detection, root-recovery, and total-work timing without changing detector thresholds. The resource-refuel Debug surface remains the calibration/test owner for route timings and retry count; Macro Plan Utilities call the same Automation service with a selected station set and saved interval. Scheduled entry accepts only a verified Lobby or owned shared-Play surface, closes any verified Challenge selector and remaining Play layers through detector-owned Back actions, then uses Areas → Lobby → Spawn and requires stable Lobby proof before continuing. Scheduled completion never opens Play: it enters Areas directly from the station panel and follows the same Lobby-category and Spawn actions.
